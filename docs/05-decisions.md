| 27 | **Course → Google Calendar is a prefilled link, never an API write.** The course row links to `calendar.google.com/render` with the series filled in. (2026-08-16, narrows OPEN H. | 30 | **Interactions get their own table.** `contact_interactions(contact_id, date, note)` with `ON DELETE CASCADE`; logging inserts a history row **and** advances `contacts.last_contacted` via `MAX(COALESCE(last_contacted, ?), ?)` in one transaction. `next_followup` is never stored — `src/lib/professional/followup.ts` computes it and delegates label + colour to `dueInfo()`. No `channel`/kind enum. (2026-08-17) | The user's call over the smaller "just bump last_contacted" option: an interaction note is the CRM's actual content and isn't reconstructable later. The `MAX` is load-bearing — back-dating an interaction must record history without dragging the contact back into the overdue block. Storing `next_followup` would give it two writers (interval edits, interaction logs) and therefore a staleness bug; a generated column would split the `+interval` math from the colour math, which is exactly the `pace.ts` failure. No `channel` enum for decision #25's reason: a kind that is never filtered on is a field to maintain, and `note` carries "coffee at Sprüngli" for free. |
| 31 | **The day-job project is identified by config key `professional.day_job_project_id`, not by name or a new column.** `dayJobProject()` is the single accessor; `portfolioProjects()` is defined as "professional projects minus that one". (2026-08-17) | Day job is a `projects` row only as a filing mechanism, so listing it under "building · portfolio evidence" is both a category error and a restatement of the section directly above it — the "Up next" / schedule-check pattern (#28) pre-committed. Name-matching was rejected on the 2026-08-16 learning (prefer editable config over config-that-can't-change) and a `projects.kind` column as an enum maintained forever to distinguish one row. Both consumers reading one accessor means they cannot drift apart; a key pointing at a deleted project resolves to `undefined` and the page degrades honestly rather than breaking. The seed is guarded on the key's own absence, not on an empty `projects` table — that branch never fires again on an existing database. |
| 32 | **Learning items carry `started` + `completed`, both hand-editable, and no target date.** Status is stored as the settled enum and displayed through `LEARNING_STATUS_LABEL` as "Not learned / Learning / Learned / Dropped". (2026-08-17) | The user asked to be able to "put a topic, date, link to external material, status", and chose started/completed over a new `target` column when offered both. Flipping the status stamps a date only when it is still empty, so the common path needs no typing and a typed date is never overwritten. His words for the markers beat the internal slugs, and one exported map means no surface re-words them. |
| 33 | **Phone capture is an iOS Shortcut appending to a synced file — no Notion, no cloud mailbox.** The Shortcut (Siri-triggerable) writes one JSON line per capture to a file in iCloud Drive; a launchd job and the app's Sync button ingest new lines into `inbox`. (2026-08-17, reopens and replaces #7 at the user's explicit ask) | The user's challenge was fair: the project exists to leave Notion, and keeping it as a mailbox meant an integration token to maintain, a third-party API in a daily path, and Notion still in the loop every morning — to move one line of text. Two needs were bundled in #7 and only one of them requires a cloud surface: "talk to Claude on my phone and have it land in LifeOS" does, "capture a thought from my phone" does not. Cutting Notion takes Stage 5 from three credentials to one, removes the last external dependency from the daily path, and keeps the whole capture path on hardware the user owns. Cost: no conversational splitting at capture time — recovered at ingest by #34. iCloud sync latency (seconds to minutes) replaces cron-poll latency, which is a wash for an inbox. |
| 34 | **Captures are parsed at ingest, locally, not at capture.** The raw line lands in `inbox` verbatim; a local script then calls the Anthropic API to turn it into tasks / health_metrics / notes. (2026-08-17, closes OPEN D) | Falls out of #33: with no LLM at the capture end, at-ingest is the only place parsing can happen — and it is the better half of the original trade anyway. The raw text is preserved so a bad parse is always re-runnable, the prompt can be improved without retraining a phone habit, and it reuses the `ANTHROPIC_API_KEY` the briefs already need. |
| 35 | **Stage 5 ships three briefs — world, ai_research, german_word. No Gmail, no email-todos brief.** Revisit much later; if it comes back, try an App Password + `imaplib` before a Google Cloud OAuth project. (2026-08-17, closes OPEN E) | The user's call, and the cheap one to defer: briefs are deliberately one script per kind (architecture → scheduled jobs), so adding `email_todos.py` later is a new file and a key, not a refactor, and the `briefs.kind` CHECK already accepts `'email_todos'` — no migration either. Three reasons to wait rather than build: it is the only brief needing a second credential, the only one whose data is personal, and — the part the original OPEN entry never said out loud — **the only one that would send the user's own content (email subjects and snippets) to the Anthropic API**, where nothing else in LifeOS leaves the machine. That is a bigger change to a local-first system than the OAuth paperwork, and it is not worth making for a card whose value is unknown until the other three have been lived with. A rule-based scan (sender/subject match, unanswered threads) is the recorded way to have it without sending anything out. |
